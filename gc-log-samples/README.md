# GC log samples

Generated by `gc-log-generator/generate-samples.sh` (macOS) and
`gc-log-generator/generate-samples-linux.sh` (Linux in Docker); last update 2026-11-07.
Every file is a single gzipped run of the `gc-log-generator` workload (about 35 s, fixed 512 MB heap).
File names are `<jdk>/<collector>-<locale>-<platform>.log.gz`. Collectors that a given JDK does not
provide on a given platform are skipped. The exact JVM options of every file are in
[`samples.tsv`](samples.tsv).

Platforms:

- `linux`: Linux aarch64
- `macos`: Darwin arm64

## JVM options

Common: `-Xms512m -Xmx512m` and one of `-XX:+UseParallelGC`, `-XX:+UseG1GC`, `-XX:+UseZGC`,
`-XX:+UseShenandoahGC`, `-XX:+UseShenandoahGC -XX:ShenandoahGCMode=generational`.
`-XX:+UseStringDeduplication` is added for G1 and Shenandoah, and since JDK 18 for every collector.
ZGC is generational on JDK 25+ (the only mode left) and non-generational on JDK 17.

Logging:

- **jdk8**:

  ```
  -XX:+PrintGCDetails -XX:+PrintGCDateStamps -XX:+PrintGCTimeStamps -XX:+PrintTenuringDistribution -XX:+PrintGCApplicationStoppedTime -XX:+PrintGCApplicationConcurrentTime -XX:+PrintSafepointStatistics -XX:PrintSafepointStatisticsCount=1
  -XX:+PrintStringDeduplicationStatistics   (G1 only)
  stdout is the log file
  ```

- **jdk11**:

  ```
  -Xlog:codecache=info,class+unload,class+load,os+thread,safepoint,gc*,gc+ergo=trace,gc+age=trace,gc+phases=trace,gc+humongous=trace,gc+heap=trace,gc+tlab=trace,jit+compilation=debug,codecache+sweep*=trace,gc+stringdedup=debug:file=<file>:level,tags,time,uptime:filecount=0
  ```

## Workload

Background allocation from three threads (objects with short, medium and long lifetimes, duplicated
strings) runs all the time, while these scenarios run one after another:

1. warm-up - steady young collections, aging and tenuring,
2. humongous allocations - large primitive and reference arrays, some of them kept alive,
3. old generation growth and churn - live set of ~45% of the heap that keeps changing (G1 concurrent
   cycles and mixed collections, Parallel full collections, ZGC/Shenandoah cycles),
4. class loading and unloading - 4500 classes defined in separate class loaders, some of them JIT
   compiled, then dropped (Metadata GC Threshold, class unloading, code cache sweeper on JDK 19 and older),
5. thread churn - 200 short lived threads and an expiring thread pool,
6. JIT deoptimization - broken type profiles and an unstable if (made not entrant),
7. safepoint operations - thread dumps, deadlock detection, biased lock revocation, System.gc(),
   while a counted loop delays reaching the safepoint,
8. memory pressure - heap filled with live data, then short bursts of objects that stay reachable
   (to-space exhausted, full collections, allocation stalls, degenerated cycles, handled OutOfMemoryErrors),
9. cool-down - everything released, final System.gc().

## Locale

HotSpot formats numbers in logs with the C library, so the decimal separator follows `LC_ALL`:
`en_US` files use dots, `pl_PL` files use commas (`[1,234s]`, `12,345ms`). Date stamps (the `time`
decorator, `-XX:+PrintGCDateStamps`) always use a dot. In JDK 11+ files the first few hundred lines are
written before the JVM initializes the locale, so `pl_PL` files mix both separators; JDK 8 logs its first
GC event after that point, so its `pl_PL` files use commas only.

## Regenerating

```shell
gc-log-generator/generate-samples.sh          # on macOS
gc-log-generator/generate-samples-linux.sh    # Linux, in Docker
# or a subset, e.g.:
JDKS='jdk17=corretto-17.*' COLLECTORS='g1 zgc' LOCALES=en_US gc-log-generator/generate-samples.sh
```
